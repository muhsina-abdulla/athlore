# Architecture

How Athlore is built, and why. Product intent lives in [vision.md](vision.md) and [requirements.md](requirements.md). This doc covers the technical shape that serves them.

## Decisions

| Area | Decision |
| --- | --- |
| App | Expo SDK 58, React Native 0.88, TypeScript strict, **Expo Router** (routes in `src/app/`) |
| Build | Runs in **Expo Go** today (sign-in goes through the browser, so no native module is needed). An installable build (EAS `preview` profile) is for using the app without the computer running. |
| Local storage | **SQLite** (`expo-sqlite`) + **Drizzle ORM**. The local DB is the source of truth for the UI. |
| Backend | **Supabase**: Postgres, Google auth, Row Level Security, Edge Functions (AI, later) |
| Sync | **Hand-rolled outbox**: a session is pushed whole by one all-or-nothing database function (`push_session`); lookups are upserts; pull by `updated_at` |
| State | Drizzle live queries for data, React state for forms, a small **Zustand** store for sync status. No TanStack Query. |
| Auth | Google only, through the browser: `supabase.auth.signInWithOAuth` (PKCE) opened with `expo-web-browser`, the returned code exchanged for a session. Works in Expo Go and in a built app. The session is kept in the phone's SQLite (`expo-sqlite/localStorage`). Without a `.env` the app runs on the phone alone (no sign-in, no sync). |
| AI | Phase 5. Runs in a Supabase Edge Function, so no keys ship in the app. Provider to be chosen then. |
| Migration | One-off local Node script in `scripts/migrate/`. Not an app feature. |

## Principles

1. **Local first.** Every screen reads from SQLite. Logging, history, drafts and analytics work with no network.
2. **Never lose an entry.** Drafts are durable rows, writes are queued, and retries are idempotent. A draft counts as submitted only on server acknowledgement.
3. **AI is a layer on top.** Nothing in the journal, history or analytics depends on it.
4. **Single user, no tenancy features.** Every row still carries `user_id` with RLS, because that costs nothing and keeps the data private.

## Data model

Every synced table has `id uuid` (generated on the client), `user_id` (server only: the local database does not store it, and the server sets it from the signed-in user), `created_at`, `updated_at` (set by a server trigger) and `deleted_at` (soft delete, so deletions sync). Postgres and SQLite carry the same columns.

### Sessions

**`sessions`**
- `training_date` *(date)*: drives all sorting, history and analytics
- `category_id`: required, except on migrated rows (see below)
- `training_focus`
- `duration_minutes` *(int, nullable)*
- `duration_raw` *(text, nullable)*: the legacy value, verbatim
- `techniques`, `self_assessment`, `coach_feedback`, `coach_name`, `injury_notes`, `proud_of`, `to_improve` *(text)*
- `rating` *(1–10, nullable)*
- `mood_scale` *(1–5, nullable)*, `mood_text` *(nullable)*
- `source` *(`app` | `legacy`)*
- `submitted_at`: the moment the entry was first submitted, separate from `training_date` and `created_at`

**Related tables**
- `categories` (`name`) and `user_session_types` (`name`): the shared defaults plus the athlete's own entries
- `session_type_assignments` (`session_id`, `session_type_id`): which types a session has (many-to-many)

### Exercises

**Tables**
- `exercises`: the library (`name`, `is_custom`, `muscle_group`, `default_kind`). A master list ships with the app (fixed ids, in `src/db/defaultExercises.ts`); the athlete adds custom ones on top. Names are unique regardless of letter case, so typing a master exercise name picks the master one.
- `session_exercises` (`session_id`, `exercise_id`, `position`, `notes`)
- `exercise_sets`:
  - `session_exercise_id`, `position`, `kind`, `is_top`
  - value columns, all nullable: `reps`, `weight`, `weight_unit`, `added_load`, `duration_seconds`, `distance_m`

**How the form maps to it:** the log form keeps each set as `reps` plus one "main number" (`amount`), and the exercise's kind decides which column that number is saved to (weight, added load, seconds or metres). A session's exercises are saved as a whole list: saving replaces the previous list (sets go with their exercise via cascade), and sets with nothing entered are dropped.

**Repeated sets:** a row in the set table can carry a count ("× 3"). On save it becomes that many identical set rows (the first keeps the row's id, the others get new ones), capped at 20; a repeated row is never a top set. When a saved session is opened, consecutive identical sets (same reps and number, none top) fold back into one row. Nothing about the count is stored.

**Removing categories and session types:** only entries that no non-deleted session uses can be removed, and removal is a soft delete that syncs. Sessions that were themselves deleted do not block it, and they keep pointing at the removed entry, so history stays intact. Retired defaults are shared server rows (`user_id` is null) that the app is not allowed to update, so the sync worker must never push a soft delete for a default id; the "update defaults" migration hides them on the server.

**Deleting a session** is a soft delete: the session, its exercises and its sets stay in the database with `deleted_at` set on the session, and the deletion is queued so the server hides it too.

**Sync note:** because exercises and sets are replaced as a whole, the sync worker must replace a session's children on the server too (delete the ones no longer present, upsert the rest), not only upsert.

**Set kinds** (`kind`)

| `kind` | Uses | Shown as |
| --- | --- | --- |
| `reps_weight` | `reps`, `weight`, `weight_unit` | 8 × 60 kg |
| `added_load` | `reps`, `added_load`, `weight_unit` | 8 × +10 kg |
| `bodyweight` | `reps` | 12 reps |
| `time` | `duration_seconds` | 60s |
| `distance` | `distance_m` | 25 m |

### Goals (Phase 3, sketched so the schema has room)

**Tables**
- `goals` (`title`, `position`, `archived_at`)
- `milestones`:
  - `goal_id`, `position`
  - `kind`: `measurable` | `skill`
  - `criteria` *(json)*: only for measurable milestones
  - `completed_at`, `completed_by` (`auto` | `manual`)
- `milestone_sessions` (`milestone_id`, `session_id`)

**Rule:** measurable milestones are evaluated locally whenever sessions change.

### Local-only tables (SQLite)

- `drafts`:
  - `id`
  - `target_session_id`: the client UUID the session will get, or the session being edited
  - `payload` *(json of the form state)*, `updated_at`
- `outbox`:
  - `id`, `table`, `row_id`, `op` (`upsert` | `delete`)
  - `status` (`pending` | `in_flight` | `failed`), `attempts`, `last_error`, `created_at`
- `sync_meta`: `last_pulled_at` per table

### Product decisions settled here

- **Rating**
  - Stored as 1–10 and shown as 5 stars. Each point is half a star (7 = three and a half stars), and either half of a star can be tapped.
  - Tapping the current value again clears the rating.
  - Legacy values keep their original numbers.
- **Mood**
  - New entries use `mood_scale`: 1 Rough, 2 Low, 3 Okay, 4 Good, 5 Great. These describe emotional mood, not tiredness. Only the labels live in the app, so they can change without touching saved data.
  - Legacy mood goes verbatim into `mood_text` with `mood_scale = null`.
  - Neither field is ever derived from the other.
- **Category on migrated rows**
  - `category_id` is nullable only when `source = 'legacy'`. A Postgres CHECK constraint enforces this.
  - History offers to tag uncategorised sessions later.
- **Exercise sets:** a per-set `kind` decides which value columns apply (see the set kinds table above).

## Drafts and submission flow

1. **Open Log.** Create (or resume) a `drafts` row keyed by a fresh session UUID. That UUID is the session's ID for life.
2. **Typing.** Debounced (~500 ms) writes of the form state into `drafts.payload`. Also written when the app goes to the background and when the screen closes. The header shows "Draft saved". An untouched form never becomes a draft.
3. **Save session.** In one SQLite transaction:
   - upsert the session and replace its session types
   - enqueue an outbox entry (one per entity, so saving again replaces it)
   - delete the draft

   The transaction is all-or-nothing. If it fails, nothing is written and the draft is untouched.
   From here the session is a local row with `submitted_at = null` and a pending outbox entry. History shows it as "Waiting to sync". It is not submitted yet, and it is recoverable and editable.
4. **Push.** The worker upserts to Supabase `on conflict (id)`, so a retry can't duplicate anything.
5. **Server acknowledgement.**
   - Set `submitted_at` (on first submit).
   - Delete the outbox entry.
   - Only now is the session considered submitted.
6. **Failure.** The outbox entry stays `failed` with `last_error`. History shows "Couldn't sync · Retry" and nothing is lost.

Editing an existing session autosaves a draft only once the form differs from the saved version, and offers to continue it next time the session is opened.

**Implementation note:** the Expo SQLite driver in Drizzle runs transactions synchronously and commits as soon as the callback returns. Transaction callbacks must therefore be synchronous and end each statement in `.run()`. An `async` callback would commit after its first statement.

Edits follow the same path with the existing session ID. Deletes set `deleted_at` and enqueue an upsert.

The default categories and session types use fixed UUIDs, seeded locally and on the server, so two devices never create duplicate defaults.

## Sync

The code is in `src/sync/`. The engine (`engine.ts`) is plain logic that talks to the server through the small `RemoteApi` interface (`remote.ts`), so it can be tested against a pretend server; `supabaseRemote.ts` is the real one, and `worker.ts` decides when to run.

- **When it runs:** a moment after anything is saved (`requestSync` in `signal.ts`, called whenever something is queued), when the app opens or returns to the foreground, right after signing in, every 5 minutes while open, and on "Retry all". One run at a time; a request during a run triggers one more run afterwards.
- **Push:**
  - Entries go in order: categories, session types, exercises, then sessions, so a session never arrives before what it points at.
  - A session is saved with one call to the `push_session` database function (`supabase/migrations/20261108000000_push_session.sql`): the session and all its types, exercises and sets in a single all-or-nothing step. Children are replaced as a whole, so a retry never duplicates.
  - An entry is removed only after the server confirms, and only if the item was not edited again while the push was running (its `updated_at` is compared). Otherwise it stays queued and the newer version goes next time.
  - When the server confirms a session, its `submitted_at` is stored locally. That is the moment it counts as submitted.
  - Offline or an expired sign-in stops the run at once and leaves everything queued and untouched. A refusal from the server marks only that entry `failed` (with the reason) and the run carries on; failed entries are retried on every run.
  - The app never pushes shared defaults (they belong to the server), master-list exercises, or entries whose row no longer exists; those are just dropped from the outbox.
  - An entry left "in flight" by an app that was killed mid-push is reset and sent again.
- **Pull:**
  - Per table, in the same order, rows changed since the last pull are copied down (the first page starts 2 minutes before the saved position, in case a row committed late; re-applying a row is harmless). A fresh phone gets everything back this way.
  - A session is replaced together with its children, in one transaction.
  - A row with an unsent local change is left alone. That is checked again inside the transaction that writes it, because fetching the children takes time and an edit made meanwhile must never be overwritten by the older server copy.
  - If a row cannot be applied, the saved position is not moved past it, so it is tried again next time instead of being skipped for good. A same-named entry from elsewhere is skipped without counting as a failure.
  - Children are read page by page (the server returns at most 1000 rows per request and does not say when it cuts a result short).
- **Conflicts:** last write wins per row, except that the phone's own unsent edit always wins until it has been pushed. For one person that is enough; revisit only if editing from several devices becomes real.
- **Timestamps:** `updated_at` and `submitted_at` come from the server clock, so pull ordering never depends on the phone's clock.
- **Known limit:** a pull page is 1000 rows. More than 1000 rows sharing one exact `updated_at` would not all be fetched; a one-off migration inserts far fewer.

## Analytics

- SQL over local SQLite, in `src/features/analytics/`.
- Always grouped by `training_date`.
- "Sessions" counts rows. "Training days" counts `distinct training_date`.
- Excludes `deleted_at` rows.
- Works offline and without AI.

## AI layer (Phase 5)

- **Where it runs:** a Supabase Edge Function.
- **What it does:**
  - Retrieves the relevant records (SQL filters, plus `pgvector` embeddings of text fields if needed).
  - Calls the model.
  - Returns structured output where every item is tagged `recorded` (with source session IDs), `analysis` or `suggestion`.
- **In the app:** the UI renders the three kinds distinctly.
- **When it's unavailable:** the Insights tab says so, and nothing else in the app is affected.

## Legacy migration

**Script:** `scripts/migrate/` runs with Node on the dev machine, reading the gitignored CSV.

**Field mapping**
- `Date` → `training_date`
- `Timestamp` → `submitted_at` (and `created_at`). Never swapped, even when the timestamp comes first.
- Durations:
  - Parsed into `duration_minutes`; `duration_raw` is always kept.
  - Ambiguous values (e.g. `3.45h`) are left `null` and listed in a review file.
- All text is copied verbatim.
- `source = 'legacy'`.

**Duplicates and modes**
- Duplicates are detected by a hash of (training date, timestamp, focus) and reported, not inserted.
- **Dry-run mode** writes nothing and produces the review report.
- **Real run** writes to Supabase with the service-role key (kept in a gitignored `.env`). The app then pulls the rows like any other data.
- The report never leaves the machine.

## Environment and secrets

- `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` live in `.env` (copy `.env.example`). Both are public by design, and RLS protects the data. After changing `.env`, restart with `npx expo start --clear`.
- The service-role key is used only by the migration script. It never goes in the app.
- The Supabase session is kept in the phone's SQLite through `expo-sqlite/localStorage` (Supabase's own current Expo guide does the same).
- The Google OAuth client (a **Web application** client) lives in Google Cloud and is entered in the Supabase dashboard under Authentication > Providers > Google. Its authorized redirect URI is Supabase's callback URL. No Google keys are in the app.
- Supabase Authentication > URL Configuration must allow the address the app returns to: `exp://**` for Expo Go and `athlore://**` for a built app.

## Build and run

- Development: `npx expo start` and open the project in Expo Go (the installed Expo Go must match the SDK).
- To use the app away from the computer: `npx eas-cli@latest build --platform android --profile preview` produces an installable APK.
- Releases come later through EAS Build and EAS Update.
