# Architecture

How Athlore is built, and why. Product intent lives in [vision.md](vision.md) and [requirements.md](requirements.md). This doc covers the technical shape that serves them.

## Decisions

| Area | Decision |
| --- | --- |
| App | Expo SDK 57, React Native, TypeScript strict, **Expo Router** (routes in `src/app/`) |
| Build | **EAS development build** from Phase 2 onward (needed for native Google sign-in). Expo Go is no longer the target. |
| Local storage | **SQLite** (`expo-sqlite`) + **Drizzle ORM**. The local DB is the source of truth for the UI. |
| Backend | **Supabase**: Postgres, Google auth, Row Level Security, Edge Functions (AI, later) |
| Sync | **Hand-rolled outbox**: push with idempotent upserts by client UUID, pull by `updated_at` |
| State | Drizzle live queries for data, React state for forms, a small **Zustand** store for sync status. No TanStack Query. |
| Auth | Google only: `@react-native-google-signin/google-signin` → `supabase.auth.signInWithIdToken` |
| AI | Phase 5. Runs in a Supabase Edge Function, so no keys ship in the app. Provider to be chosen then. |
| Migration | One-off local Node script in `scripts/migrate/`. Not an app feature. |

## Principles

1. **Local first.** Every screen reads from SQLite. Logging, history, drafts and analytics work with no network.
2. **Never lose an entry.** Drafts are durable rows, writes are queued, and retries are idempotent. A draft counts as submitted only on server acknowledgement.
3. **AI is a layer on top.** Nothing in the journal, history or analytics depends on it.
4. **Single user, no tenancy features.** Every row still carries `user_id` with RLS, because that costs nothing and keeps the data private.

## Data model

Every synced table has `id uuid` (generated on the client), `user_id`, `created_at`, `updated_at` (set by a server trigger) and `deleted_at` (soft delete, so deletions sync). Postgres and SQLite carry the same columns.

### Sessions

**`sessions`**
- `training_date` *(date)*: drives all sorting, history and analytics
- `category_id`: required, except on migrated rows (see below)
- `training_focus`
- `duration_minutes` *(int, nullable)*
- `duration_raw` *(text, nullable)*: the legacy value, verbatim
- `techniques`, `self_assessment`, `coach_feedback`, `injury_notes`, `proud_of`, `to_improve` *(text)*
- `rating` *(1–10, nullable)*
- `mood_scale` *(1–5, nullable)*, `mood_text` *(nullable)*
- `source` *(`app` | `legacy`)*
- `submitted_at`: the moment the entry was first submitted, separate from `training_date` and `created_at`

**Related tables**
- `categories` (`name`) and `session_types` (`name`): seeded defaults plus custom entries
- `session_session_types` (`session_id`, `session_type_id`): many-to-many

### Exercises

**Tables**
- `exercises`: the library (`name`, `is_custom`)
- `session_exercises` (`session_id`, `exercise_id`, `position`, `notes`)
- `exercise_sets`:
  - `session_exercise_id`, `position`, `kind`, `is_top`
  - value columns, all nullable: `reps`, `weight`, `weight_unit`, `added_load`, `duration_seconds`, `distance_m`

**Set kinds** (`kind`)

| `kind` | Uses | Shown as |
| --- | --- | --- |
| `reps_weight` | `reps`, `weight`, `weight_unit` | 8 × 60 kg |
| `added_load` | `reps`, `added_load`, `weight_unit` | 8 × +10 kg |
| `bodyweight` | `reps` | 12 reps |
| `time` | `duration_seconds` | 60s |
| `distance` | `distance_m` | 25 m |

### Goals (Phase 3, sketched so the schema has room)

**Tables**
- `goals` (`title`, `position`, `archived_at`)
- `milestones`:
  - `goal_id`, `position`
  - `kind`: `measurable` | `skill`
  - `criteria` *(json)*: only for measurable milestones
  - `completed_at`, `completed_by` (`auto` | `manual`)
- `milestone_sessions` (`milestone_id`, `session_id`)

**Rule:** measurable milestones are evaluated locally whenever sessions change.

### Local-only tables (SQLite)

- `drafts`:
  - `id`
  - `target_session_id`: the client UUID the session will get, or the session being edited
  - `payload` *(json of the form state)*, `updated_at`
- `outbox`:
  - `id`, `table`, `row_id`, `op` (`upsert` | `delete`)
  - `status` (`pending` | `in_flight` | `failed`), `attempts`, `last_error`, `created_at`
- `sync_meta`: `last_pulled_at` per table

### Product decisions settled here

- **Rating**
  - Stored as 1–10 and shown as 5 stars with half-stars (`rating / 2`).
  - New entries save whole stars as 2, 4, … 10.
  - Legacy values keep their original numbers.
- **Mood**
  - New entries use `mood_scale`: 1 Drained, 2 Flat, 3 Okay, 4 Good, 5 Great.
  - Legacy mood goes verbatim into `mood_text` with `mood_scale = null`.
  - Neither field is ever derived from the other.
- **Category on migrated rows**
  - `category_id` is nullable only when `source = 'legacy'`. A Postgres CHECK constraint enforces this.
  - History offers to tag uncategorised sessions later.
- **Exercise sets:** a per-set `kind` decides which value columns apply (see the set kinds table above).

## Drafts and submission flow

1. **Open Log.** Create (or resume) a `drafts` row with a fresh `target_session_id` UUID. That UUID is the session's ID for life.
2. **Typing.** Debounced (~500 ms) writes of the form state into `drafts.payload`. The header shows "Draft saved".
3. **Save session.** In one SQLite transaction:
   - write the session and its child rows
   - enqueue outbox entries
   - mark the draft `pending_sync` (it is kept, not deleted)
4. **Push.** The worker upserts to Supabase `on conflict (id)`, so a retry can't duplicate anything.
5. **Server acknowledgement.**
   - Set `submitted_at` (on first submit).
   - Delete the outbox entries.
   - Delete the draft.
   - Only now is the session considered submitted.
6. **Failure.** The entry stays `failed` with `last_error`. History shows "Couldn't sync · Retry" and the draft is still recoverable.

Edits follow the same path with the existing session ID. Deletes set `deleted_at` and enqueue an upsert.

## Sync

- **Triggers:** app start, app returns to the foreground, network reconnects, after every save, and manual "Retry all".
- **Push:**
  - Drain the outbox in order, children after parents.
  - Back off exponentially on failure.
- **Pull:**
  - Per table, select rows with `updated_at > last_pulled_at` and upsert them locally.
  - Rows with pending outbox entries are skipped so a pull doesn't overwrite local unsynced work.
- **Conflicts:** last write wins per row. For one user on one phone that's enough. Revisit only if multi-device editing becomes real.
- **Timestamps:** `updated_at` comes from the server clock (trigger), so pull ordering doesn't depend on the phone's clock.

## Analytics

- SQL over local SQLite, in `src/features/analytics/`.
- Always grouped by `training_date`.
- "Sessions" counts rows. "Training days" counts `distinct training_date`.
- Excludes `deleted_at` rows.
- Works offline and without AI.

## AI layer (Phase 5)

- **Where it runs:** a Supabase Edge Function.
- **What it does:**
  - Retrieves the relevant records (SQL filters, plus `pgvector` embeddings of text fields if needed).
  - Calls the model.
  - Returns structured output where every item is tagged `recorded` (with source session IDs), `analysis` or `suggestion`.
- **In the app:** the UI renders the three kinds distinctly.
- **When it's unavailable:** the Insights tab says so, and nothing else in the app is affected.

## Legacy migration

**Script:** `scripts/migrate/` runs with Node on the dev machine, reading the gitignored CSV.

**Field mapping**
- `Date` → `training_date`
- `Timestamp` → `submitted_at` (and `created_at`). Never swapped, even when the timestamp comes first.
- Durations:
  - Parsed into `duration_minutes`; `duration_raw` is always kept.
  - Ambiguous values (e.g. `3.45h`) are left `null` and listed in a review file.
- All text is copied verbatim.
- `source = 'legacy'`.

**Duplicates and modes**
- Duplicates are detected by a hash of (training date, timestamp, focus) and reported, not inserted.
- **Dry-run mode** writes nothing and produces the review report.
- **Real run** writes to Supabase with the service-role key (kept in a gitignored `.env`). The app then pulls the rows like any other data.
- The report never leaves the machine.

## Environment and secrets

- `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` live in `.env`. Both are public by design, and RLS protects the data.
- The service-role key is used only by the migration script. It never goes in the app.
- The Supabase session is persisted with `expo-secure-store`.
- Google OAuth client IDs (Android + web) go in `app.json` config / `.env`.

## Build and run

- Development: `eas build --profile development --platform android` once, then `npx expo start --dev-client`. Rebuild only when native dependencies change.
- Releases come later through EAS Build and EAS Update.
